# Website Wording Rules

Apply Nicholas Sinn’s wording preferences to this website. Choose the register by what the reader is doing.

## Interface and administration

- Use familiar, direct labels and actions. Examples: **Change Reason**, **Audience**, **Assigned to You**, **Time to Respond**.
- Keep a clear existing label; do not rename controls only for variety. **When / Who**, **Discard**, **Link Text**, and **Today** were specifically retained in their original contexts.
- Keep helpers that explain a useful task, state, condition, or consequence here. Remove generic introductions, repeated context, reassurance, and explanations of obvious controls.
- Do not choose the shortest version automatically. Useful syntax examples and compact accepted-value/default references can stay.
- State actual outcomes: queued is not sent; opening setup is not completing it; unknown is not failed. Keep actors, conditions, counts, and material consequences accurate.
- Errors do not share one mandatory formula. **Change Reason Required**, **Must Select a Test Account**, and **Unable to Confirm Email Status** fit different contexts.

## Tutorials and guidance

- Use practical task headings and instructions in the order the interface actually requires.
- Use current control names when quoting controls. A task heading can repeat an instruction in the body.
- Use *please* where it adds natural courtesy; do not force or ban it.
- Keep a prerequisite or consequence when it matters. Omit secondary explanations when the task and surrounding controls already provide enough context.
- For technical reference, preserve useful literal syntax, accepted inputs, mappings, and default conditions.

## Public pages and site emails

- Write plain, welcoming prose. Public descriptions can be warmer and fuller than admin labels.
- Explain the actual service and useful next step without slogans, inflated claims, conversational filler, or internal implementation detail.
- Use verified names, service boundaries, commitments, and facts. Do not copy another site’s roles, eligibility, deadlines, privacy claims, or promises as if they apply here.
- In transactional emails, preserve variables, links, recipients, review stages, and real deadlines. A useful opening is welcome; generic *quick reminder* padding is unnecessary.

## Exact choices and working method

- Nicholas’s latest explicit wording controls the same fact pattern. Preserve manual edits, permanent overrides, specifically approved wording, and authoritative policy/safety content unless the task authorizes a change.
- If approved wording conflicts with a fact or interface rule, resolve that specific conflict. Do not silently change behavior, permissions, validation, or data to make a sentence true.
- Check existing field limits, variables, requiredness, and formatting before proposing alternatives for a constrained interface. Distinguish a literal token example in a caption from a runtime variable. A simple rewrite of supplied prose does not need a full site audit.
- A large audit should match the actual registry/source key set, including generated fields and saved overrides. Count site fields, email leaves, and non-text items separately.
- The SPILL batch’s form exclusions and flexible 60–70% rewrite goal are contextual history, not universal rules for every site or task.
- Ask about genuinely unsettled preferences with four real alternatives; show context when needed. Do not reopen settled examples or ask permission for routine authorized wording edits.
- Follow the local capitalization and punctuation pattern. Avoid blanket title case, blanket deletion of helpers, and cosmetic changes to meet a percentage.
